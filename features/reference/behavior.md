# Behavior & Rules Reference

**Living snapshot** of **Trips** product rules currently in force (imported baseline).

These files answer: *"What rules does Trips enforce right now?"*  
They do **not** authorize new scope — implement only from `features/feature-*.md`.

| File | Role |
|------|------|
| [api.md](./api.md) | Routes / payloads |
| [data-model.md](./data-model.md) | Tables / columns |
| **This file** | Ownership, status machines, validation, UI rules |

| System Admin maintains email types (type code, description, event code). The existing template form and list add **Email type**. **Function code** is **Scheduled** or **Send Now**. Org Admin saves a template for an organization they administer, with subject, from email, and email body. This does not send mail | `emailType`, `emailTemplate.emailTypeId`, `emailTemplate.emailBody`, `EmailTypesList`, `EmailTemplateFormDialog` | Feature 39 |
| System Admin maintains email tokens (token code, description, value source). Templates write a token as `{{TOKEN_CODE}}`. The template form has **Insert token** beside **Subject** and **Email body**; choosing one inserts the token at the cursor (or at the end). One server function builds token values from the organization, trip, optional participant, and primary trip leader, then replaces tokens; missing values become empty and unknown tokens stay as written. Dates read like `October 1, 2026`, money like `$1,000.00`, phones as `+code number`. **Preview** picks a trip and an optional participant and shows **From email**, **Subject**, and **Email body** with tokens replaced. Preview sends no email | `emailToken`, `emailTokenValues.js`, `POST /trips/email-templates/preview`, `EmailTokensList`, `EmailTemplateFormDialog`, `EmailTemplatePreviewDialog` | Feature 40 |
| Organization templates have a required **To** directly after **From email**. It lists recipients separated by commas; each is an email address or an email token (value source Organization email, Participant email, or Primary trip leader email). An **Insert token** dropdown beside **To** lists only those email tokens. **Copy from** copies **To**. Preview shows **To** after **From email** with tokens replaced, leaving out recipients that come out empty. **From email** holds exactly one email address or email token; its own **Insert token** list replaces the field with the chosen token, and Preview shows it replaced. Nothing is sent | `emailTemplate.toAddress`, `recipientsAreValid` / `senderIsValid` / `substituteRecipients` in `emailTokenValues.js`, `EmailTemplateFormDialog`, `EmailTemplatePreviewDialog` | Feature 41 |
| A **Scheduled** organization template has a required **Schedule** directly after **Function code**: **Daily**, **Weekly (Tuesday)**, or **Days before trip start**, which shows **Days before trip start** (whole number 1–365). **Send Now** templates store no schedule. **Copy from** copies the schedule. The template list shows a **Schedule** column (`Daily`, `Weekly (Tuesday)`, `N days before trip start`). The template seed gives the weekly schedule to the application-incomplete, deposit-due, and payment-due templates, and 5 days before trip start to pre-departure. Nothing is sent | `emailTemplate.scheduleRule`, `emailTemplate.scheduleDaysBefore`, `EmailTemplateFormDialog`, `EmailTemplatesList`, `seedEmailTemplates.js` | Feature 42 |
| One server service sends a template to one trip participant as plain text, filling tokens in **From email**, **To**, **Subject**, and **Email body** with the Preview functions. No recipients after filling → skipped "No recipients."; empty **From email** → skipped "No sender." `.env` chooses delivery: `EMAIL_MODE=file` (default, also used for any unknown value) writes one `.txt` file per email to `EMAIL_FILE_DIR` (default `backend/test-mail/`) with `Date`, `From`, `Reply-To` (when present), `To`, and `Subject` lines, a blank line, then the body; `EMAIL_MODE=smtp` sends through Nodemailer SMTP (`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, and `SMTP_USER` / `SMTP_PASSWORD` only when `SMTP_USER` is set). When `EMAIL_SENDER` is set, email is sent From it with the template's **From email** as **Reply-To**. Each email sent adds an `emailLog` row; a failed send is written to the application log and returns failed. No endpoint or screen | `emailDelivery.js` (`sendTemplateEmail`), `emailLog`, `backend/.env.example`, deploy workflow | Feature 43 |
| `npm run send-scheduled-emails` (optional `--date=YYYY-MM-DD`, `--dry-run`) sends the **Scheduled** templates due on the job date (default today in `SCHEDULED_EMAIL_TIMEZONE`, default `America/Chicago`). Trips: status **active** with no start date or a start date after the job date. A trip uses its own Scheduled templates and its organization's Scheduled templates for email types it has none of. Due: **Daily** every day, **Weekly** on Tuesday, **Days before trip start** when the start date is exactly that many days later. Recipients are **Trip Participant** assignments by event code: `application-incomplete` → status incomplete; `deposit-due` → approved, deposit above $0, raised below deposit; `payment-due` → approved, amount owed above $0; `pre-departure` → approved. Other event codes send nothing. Each participant handled is recorded (sent, skipped, failed); sent and skipped are not repeated for that date, failed are retried on the next run. A failure does not stop the job. Dry run prints one line per email and sends and records nothing. A summary goes to the application log and console. Production runs it from a `systemd` timer at 7:00 AM America/Chicago | `scheduledEmails.js` (`runScheduledEmails`), `sendScheduledEmails.js`, `scheduledEmailSend`, `trips-scheduled-emails.service` / `.timer`, deploy workflow | Feature 44 |
| **Send Now** templates send when their email type's event happens, to the **Trip Participant** on the trip (other roles send nothing). A trip uses its own Send Now templates for the event's email type, otherwise its organization's (no trip); **Scheduled** templates never send from events. Application events by status before → after a save: `application-started` created incomplete; `application-submitted` created applied, or incomplete → applied; `application-approved` created approved, or any other status → approved. Checked after participant apply and application edit, and staff add and update of trip people roles. Donation events on a new donation with a participant who has a Trip Participant application on the trip: `donation-received` always; `deposit-received` when the trip deposit is above $0 and amount raised goes from below to at least the deposit; `payment-complete` when amount owed goes from above $0 to $0. Every event a donation causes sends. Checked after staff and public donation create. Emails send after the save and before the response; skipped or failed emails and errors never change the response or undo the save (errors go to the application log). Every template email sent (event and scheduled) stores its template, trip, and participant on the `emailLog` row; deleting any of them keeps the row. Backend tests write mail to `backend/test-mail-test/` | `eventEmails.js` (`sendEventEmails`, `sendApplicationEventEmails`, `sendDonationEventEmails`), `tripPeopleRole.controller.js`, `tripBrowse.controller.js`, `tripDonation.controller.js`, `dashboard.controller.js` | Feature 45 |
| Each trip with leaders has one **primary trip leader**. Add trip and Edit trip show **Primary trip leader** right after **Trip leaders** once a leader is selected; it defaults to the first leader and moves to the first remaining leader when the primary is removed. Copy trip copies it. Existing trips use their earliest leader assignment | `tripPeopleRole.isPrimaryLeader`, `useTripLeaderPicker`, `AddTripDialog`, `EditTripDialog`, `ensureSchema` | Feature 40 |
| Document types may require a **document number** and carry **instructions**; add-document UI shows instructions when set and shows **Document number** only when required (otherwise hidden / stored null); application `applied` requires uploaded document files (and role-required type when set); catalog `type` includes **Diploma** (`diploma`) | `documentType.documentNumberRequired` / `instructions` / `type`, `personDocument.documentNumber`, `DocumentTypeFormDialog`, `PersonDocumentsCard`, apply/edit application | Feature 22, Feature 24 |
| **Allow Specialization** on a document type shows a Specializations section when entering that person document. Each specialization has a name, a date, and its own file. The section is hidden when the box is unchecked. A specialization file does not replace the person document file or change application submit rules | `documentType.allowSpecialization`, `personDocumentSpecialization`, `DocumentTypeFormDialog`, `PersonDocumentsCard` | Feature 34 |
| Add person and Edit person list documents or show **No documents**. **Add Document** (and row **Edit**) opens the document form in a dialog with **Save** and **Cancel**. On Add person the button stays disabled until the person is saved | `PersonDocumentsCard`, `AddPersonDialog`, `EditPersonDialog` | Feature 35 |
| When **Have allergies?** is Yes, **Allergies description** shows the hint **Enter any medicine, food, or seasonal allergies.** The field stays hidden when the answer is No or unanswered | `PersonProfileFields` | Feature 36 |
